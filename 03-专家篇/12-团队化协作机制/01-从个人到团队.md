## 15.1 理论要点：自动化的高级形态

### 15.1.1 核心观点

**自动化的高级形态不是完全没有人，而是正常路径少打扰人，异常路径能及时找到正确的人。**

### 15.1.2 个人 vs 团队的关键差异

| 维度 | 个人使用 | 团队服务 |
|------|----------|----------|
| **推送目标** | 个人通知 | 团队群 + 分类频道 |
| **决策边界** | 自己判断 | 主编确认后分发 |
| **故障处理** | 自己处理 | 有 owner 和 backup |
| **变更管理** | 随时改 Prompt | 需测试后生效 |
| **成本归属** | 个人账户 | 团队预算 |
| **权限控制** | 无 | 角色权限 |

### 15.1.3 团队化三要素

1. **明确 owner**：谁负责、谁 backup
2. **建立运行手册**：失败时如何处理
3. **设置权限**：谁能修改配置

## 15.2 实战案例：团队热点选题工作流

### 15.2.1 场景描述

**团队**：内容团队 5 人（1 主编 + 4 内容创作者）  
**需求**：每日热点自动聚合，分类审核，推送到对应频道

### 15.2.2 架构设计

```
数据源层：4个数据源
    ↓
聚合层：豆包 + WorkBuddy
    ↓
分类层：AI工具 / AI Coding / 行业动态 / 深度观察
    ↓
审核层：主编确认后分发
    ↓
推送层：对应频道 + @负责人
```

### 15.2.3 飞书多维表格设计

```
表格名称：团队热点选题池

字段定义：
├── 日期（日期）
├── 类别（单选：AI工具/AI Coding/行业动态/深度观察）
├── 标题（文本）
├── 摘要（文本）
├── 来源（文本）
├── 原始链接（URL）
├── 状态（单选：待审核/已通过/已驳回/已推送）
├── 审核人（人员）
├── 审核意见（文本）
├── 推送频道（文本）
├── 推送时间（日期时间）
└── 处理人（人员）
```

### 15.2.4 自动化规则配置

**规则1：自动聚合**
```
触发条件：每天 09:00
执行动作：
1. 调用豆包 API 获取热点
2. 按类别分类
3. 写入表格，状态：待审核
4. 通知主编进行审核
```

**规则2：审核通过后推送**
```
触发条件：【状态】更新为"已通过"
执行动作：
1. 提取该行所有字段
2. 拼接为推送消息格式
3. 推送到【推送频道】
4. 更新【推送时间】和【推送结果】
```

**规则3：审核驳回通知**
```
触发条件：【状态】更新为"已驳回"
执行动作：
1. 发送飞书消息给【创建人】
2. 消息包含【审核意见】
```

## 15.3 权限与变更管理

### 15.3.1 权限配置

| 角色 | 权限 | 说明 |
|------|------|------|
| **内容创作者** | 查看、编辑（自己的行） | 可提交选题 |
| **主编** | 查看、编辑、审核（所有行） | 可审核和分发 |
| **管理员** | 全部权限 | 可修改配置 |
| **豆包机器人** | 读取、写入（通过 API） | 执行自动化任务 |

### 15.3.2 变更流程

```
1. 提出变更申请（修改数据源/Prompt/推送配置）
2. 管理员审批
3. 测试环境验证
4. 生产环境发布
5. 记录变更日志
```

**变更内容必须记录**：
- 变更时间
- 变更人
- 变更内容
- 测试结果
- 回滚方案

## 15.5 常见错误

| 错误 | 后果 | 纠正方法 |
|------|------|----------|
| 无 owner | 失败后无人处理 | 明确 owner 和 backup |
| 权限混乱 | 数据泄露或误操作 | 遵循最小权限原则 |
| 无变更流程 | 随意修改导致不稳定 | 修改需测试后生效 |
| 个人工具直接丢给团队 | 无法满足团队需求 | 评估团队协作需求 |
| 无备份处理人 | owner 休假时任务停摆 | 指定 backup |
