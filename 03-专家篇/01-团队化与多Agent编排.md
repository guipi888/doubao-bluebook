## 6.1 理论要点：自动化的高级形态

### 6.1.1 核心观点

**自动化的高级形态不是完全没有人，而是正常路径少打扰人，异常路径能及时找到正确的人。**

### 6.1.2 个人 vs 团队的关键差异

| 维度 | 个人使用 | 团队服务 |
|------|----------|----------|
| **推送目标** | 个人通知 | 团队群 + 分类频道 |
| **决策边界** | 自己判断 | 主编确认后分发 |
| **故障处理** | 自己处理 | 有 owner 和 backup |
| **变更管理** | 随时改 Prompt | 需测试后生效 |
| **成本归属** | 个人账户 | 团队预算 |

### 6.1.3 团队化三要素

1. **明确 owner 和 backup**
   - 谁负责日常运行
   - 谁在 owner 不在时 backup
   - 升级路径（解决不了找谁）

2. **建立运行手册**
   - 失败时如何处理
   - 常见问题 FAQ
   - 紧急联系人列表

3. **设置权限和变更流程**
   - 谁能修改 Prompt
   - 谁能调整数据源
   - 修改后如何测试生效

## 6.2 实战案例：团队热点选题工作流

### 6.2.1 场景描述

内容团队 5 人，每天需要：
- 从多个数据源聚合热点
- 按类别分类（AI工具 / AI Coding / 行业动态）
- 主编审核后分发到对应频道

### 6.2.2 架构设计

```
数据源层：4个数据源（个人→团队，不变）
    ↓
聚合层：豆包 + WorkBuddy（个人→团队，不变）
    ↓
分类层：AI工具 / AI Coding / 行业动态（新增）
    ↓
审核层：主编确认后分发（新增）
    ↓
推送层：对应频道 + @负责人
```

### 6.2.3 飞书多维表格实现

**表格设计**：
```
表格名称：团队热点选题池

字段：
├── 日期（日期）- 自动填充
├── 类别（单选）- AI工具 / AI Coding / 行业动态
├── 标题（文本）
├── 摘要（文本）
├── 来源（文本）- 如"微信公众号 + GitHub"
├── 建议角度（文本）
├── 状态（单选）- 待审核 / 已通过 / 已驳回 / 已推送
├── 审核人（人员）
├── 驳回原因（文本）
└── 推送时间（日期时间）
```

**自动化规则**：

规则1：自动分类
```
触发条件：新行添加到表格
执行动作：
1. 读取【标题】和【摘要】
2. 调用豆包判断类别（AI工具/AI Coding/行业动态）
3. 填入【类别】字段
```

规则2：主编审核
```
触发条件：【状态】更新为"已通过"
执行动作：
1. 提取该行所有字段
2. 拼接为频道消息格式
3. 推送到对应频道
4. @对应负责人
5. 更新【推送时间】为当前时间
```

规则3：每日待审核提醒
```
触发条件：每天 10:00
执行动作：
1. 筛选【状态】= "待审核" 的行
2. 生成待审核视图
3. 发送给主编
```

## 6.3 多Agent编排设计

### 6.3.1 什么是多Agent编排

**单Agent**：一个豆包实例处理所有步骤
**多Agent**：多个 specialized Agent 各司其职

### 6.3.2 多Agent架构

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  采集Agent   │    │  过滤Agent   │    │  审核Agent   │
│  (Fetcher)  │    │  (Filter)   │    │  (Reviewer) │
└──────┬──────┘    └──────┬──────┘    └──────┬──────┘
       │                  │                  │
       ▼                  ▼                  ▼
  数据源1..4        四维过滤            主编确认
       │                  │                  │
       └──────────────────┼──────────────────┘
                          ▼
                   ┌─────────────┐
                   │  编排Agent   │
                   │ (Orchestrator)│
                   └─────────────┘
```

### 6.3.3 Agent 职责划分

| Agent | 职责 | 输入 | 输出 | 容错 |
|-------|------|------|------|------|
| **采集Agent** | 从数据源获取原始数据 | 数据源列表 | 原始条目列表 | 部分失败标记缺失 |
| **过滤Agent** | 四维过滤 + 去重 | 原始条目 | 有效条目 | 过滤后不足则 blocked |
| **审核Agent** | 主编确认后分发 | 有效条目 | 审核结果 | 驳回则返回修改 |
| **编排Agent** | 协调各Agent，管理状态机 | 任务指令 | 最终结果 | 任一Agent失败则告警 |

### 6.3.4 编排逻辑

```python
class Orchestrator:
    def run_daily_task(self):
        # 1. 采集
        raw_items = self.fetcher.fetch_all_sources()
        
        # 2. 过滤
        filtered_items = self.filter.apply(raw_items)
        if len(filtered_items) < 5:
            self.alert.blocked("内容不足")
            return
        
        # 3. 分类
        categorized = self.classifier.categorize(filtered_items)
        
        # 4. 写入表格
        self.db.write(categorized)
        
        # 5. 等待审核
        approved = self.reviewer.wait_for_approval()
        
        # 6. 推送
        self.deliverer.push(approved)
```

## 6.4 团队化检查清单

```
□ 明确 owner 和 backup（谁负责、谁 backup）
□ 建立运行手册（失败时如何处理）
□ 设置权限（谁能修改 Prompt、谁能调整数据源）
□ 制定变更流程（修改数据源需测试后生效）
□ 设置成本预算和告警
□ 定期复盘（每月检查指标趋势）
□ 培训 backup 人员
□ 建立升级路径（解决不了找谁）
```

## 6.6 常见错误

| 错误 | 后果 | 纠正方法 |
|------|------|----------|
| 个人任务直接丢给团队 | 无人负责、权限混乱 | 先明确 owner 和权限，再扩展 |
| 无变更流程 | 随意修改导致不稳定 | 修改数据源/Prompt 需测试后生效 |
| 无 backup 处理人 | owner 休假时任务停摆 | 指定 backup，并同步培训 |
| Agent 职责不清 | 多个 Agent 做同一件事 | 明确每个 Agent 的输入输出 |
| 过度编排 | 简单任务复杂化 | L3 以下用单 Agent，L4+ 考虑多 Agent |
